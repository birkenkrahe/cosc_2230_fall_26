* Appendix: If you need a kick for this assignment

The harmonic numbers you're computing in this assignment aren't just a
textbook exercise - they sit right next to one of the most famous open
problems in mathematics.

=H_n = 1 + 1/2 + 1/3 + ... + 1/n= is the =n=-th partial sum of the
*Riemann zeta function* at =s=1=: =zeta(s) = sum 1/n^s=. The harmonic
series' divergence is exactly why =zeta(s)= has a pole at =s=1= - and
that pole anchors the whole theory around the *Riemann Hypothesis*
(RH), which claims that all "interesting" zeros of =zeta(s)= lie on a
single line in the complex plane. It's one of seven Millennium Prize
Problems - unsolved since 1859, $1 million reward for a proof.

There's an even more direct link: a 2002 theorem (Lagarias) showed
that RH is *equivalent* to a purely elementary inequality involving
=H_n= and the sum of divisors of =n= - no complex analysis required,
just harmonic numbers. The "boring" sum you're timing this week is,
in a precise sense, one algebraic step away from a century-and-a-half
old unsolved problem.

** A recent, honestly-reported update (Aug 2026)

An unreleased Anthropic research model was recently asked to make a
real attempt at proving RH itself. It failed - as expected, nobody
solves a $1M problem by accident. But along the way, working on a

*This is not a proof of RH*, and nobody involved claims it's close to

** Catching the StackOverflowError

- Here is a Java solution that does not require a bash
  script. Explanation below.
  
- Put each call in a ~try~ block and catch the ~StackOverflowError~
  instead of letting the program die. The loop then goes on with the
  next =n=, so we see which of the two functions survives:
  #+begin_src java :noweb yes :noeval :tangle ../src/HarmonicCatch.java :dir ../src
    public class HarmonicCatch {

        // functions
        <<harmonicLoop>>
        <<harmonicRecursive>>

        // Main
        public static void main(String[] args)
        {
            // Increase n by a factor of 10 each time
            for (int n = 1000; n <= 100000000; n *= 10)
            {
                System.out.println("n = " + n);
                // Iterative version
                try
                {
                    System.out.println("  harmonicLoop:      " + harmonicLoop(n));
                }
                catch (StackOverflowError e)
                {
                    System.out.println("  harmonicLoop:      StackOverflowError");
                }
                // Recursive version
                try
                {
                    System.out.println("  harmonicRecursive: " + harmonicRecursive(n));
                }
                catch (StackOverflowError e)
                {
                    System.out.println("  harmonicRecursive: StackOverflowError");
                }
            }
        }
    }
  #+end_src

- What the ~catch~ does: when the call throws, Java skips the rest of
  the ~try~ block and runs the ~catch~ block instead of ending the
  program. By then the stack has unwound, so the program can carry on
  with the next =n=.

- ~StackOverflowError~ is an ~Error~, not an ~Exception~: the JVM reports
  that it has run out of stack space, not a bug in your logic.
  Catching it is fine for an experiment like this, but not normal
  practice.

- A loop inside one program can report a higher crash point than a
  fresh run. The JVM compiles hot methods while the program runs, and
  the compiled version of ~harmonicRecursive~ may use smaller stack
  frames.  Its crash point can therefore be higher, and it can change
  from run to run. To get the same crash point every time, start a new
  JVM for each =n=, as the bash script and the Python script do.

** Answer to the question

- Why does the iterative version keep working at values of =n= where the
  recursive version fails?
  #+begin_quote
  *Answer:* Each unfinished call to =harmonicRecursive(n)= occupies a
  stack frame - space for the parameter =n=, the return address, and
  other data - on the thread's call stack. This call stack has a fixed
  size set at JVM startup (you can set it with the ~-Xss~
  flag). Standard stack size has a ceiling of around 1MB. A small
  frame like this one takes 40-80 bytes per call, so 12,500 calls come
  to 500KB-1MB memory, which cannot be released until the base case is
  reached. See [[https://www.baeldung.com/java-call-stack-max-depth][baeldung, 2024]]. This is *space complexity*.
  #+end_quote

  //              <n>  number of terms, a positive integer (e.g. 1000)
  //
  // Input:   one command-line argument (args[0]), parsed with
  //          Integer.parseInt() into n.
  // Output:  one line per method with n, the harmonic number, and the
  //          elapsed time in seconds.
  //
  //            $ java -cp .:stdlib.jar HarmonicTiming 1000
  //            harmonicLoop:      n=1000, 7.485471 (0.0000000000 seconds)
  //            harmonicRecursive: n=1000, 7.485471 (0.0000000000 seconds)
  //
  //          For n around 12,600 or more the recursive call ends with
  //          a StackOverflowError (the crash point depends on the
  //          machine and its stack size).
  //
  // AI use: Claude (Anthropic) drafted this program header, and checked
  //          that the file compiles and runs under JDK 17. The
  //          Stopwatch nesting, both harmonic methods and main() are my
  //          own work.
  //
  // Pledge:  I pledge that this submission is my own work, in
  //          keeping with the Augustana academic-integrity and
  //          course AI-use policies.
  //------------------------------------------------------------
  public class HarmonicTiming
  {
      public static class Stopwatch
      {
          private final long start;

          public Stopwatch()
          {   // set stopwatch
              start = System.currentTimeMillis();
          }
          public double elapsedTime()
          {   // return time between start and now in seconds
              long now = System.currentTimeMillis();
              return (now - start) / 1000.0;
          }
      }
      // Compute harmonic numbers - iterate
      public static double harmonicLoop(int n)
      {
          double sum = 0.0;
          for (int i = 1; i <= n; i++)
              sum += 1.0/i;
          return sum;
      }
      // Compute harmonic numbers - recursive
      public static double harmonicRecursive(int n)
      {
          if (n == 1) return 1.0;
          return harmonicRecursive(n-1) + 1.0/n;
      }
      // HarmonicTiming main function
      public static void main(String[] args)
      {
          int n = Integer.parseInt(args[0]);
          // Compute and time computation using harmonicLoop
          Stopwatch timer1 = new Stopwatch();
          double result1 = harmonicLoop(n);
          double time1 = timer1.elapsedTime();
          StdOut.printf("harmonicLoop:      n=%d, %f (%.10f seconds)\n", n, result1, time1);

          // Compute and time computation using harmonicRecursive
          Stopwatch timer2 = new Stopwatch();
          double result2 = harmonicRecursive(n);
          double time2 = timer2.elapsedTime();
          StdOut.printf("harmonicRecursive: n=%d, %f (%.10f seconds)\n", n, result2, time2);
      }
  }

  /*
   ,* Why does the iterative version keep working where the recursive one
   ,* fails? Every unfinished call to harmonicRecursive() keeps a stack
   ,* frame on the call stack, and none is released until the base case is
   ,* reached; the stack has a fixed size, so at around n = 12,500 it runs
   ,* out and the JVM throws a StackOverflowError. harmonicLoop() reuses
   ,* the same few local variables no matter how large n is, so its memory
   ,* use stays constant (O(1) space versus O(n) for the recursion).
   ,*/

** A few OOP design questions

- How should =HarmonicTiming= and =Stopwatch= be nested?
  #+begin_quote
  As a *static* nested class: =public static class Stopwatch=, inside
  =public class HarmonicTiming=. The first attempt left off ~static~
  (=public class Stopwatch=), which makes it a *non-static inner class* -
  and a non-static inner class carries an invisible reference to a
  specific enclosing =HarmonicTiming= *object*, so creating one always
  means =someHarmonicTiming.new Stopwatch()=. But =main()= is ~static~, so
  no =HarmonicTiming= object exists yet when =new Stopwatch()= runs -
  there's no enclosing instance to attach to, hence: "non-static
  variable this cannot be referenced from a static context."

  Adding ~static~ removes that requirement: a *static* nested class
  doesn't carry a reference to any enclosing instance - it behaves like
  an ordinary top-level class that simply lives inside =HarmonicTiming='s
  namespace. That's exactly what's needed here, since =Stopwatch= is
  only ever used from ~static~ context (~static~ methods, called
  without ever constructing a =HarmonicTiming= object).
  #+end_quote

- Could =Stopwatch.java= itself have been the submitted file, with
  =main()= and the harmonic task functions added directly to =Stopwatch= -
  no nesting, no ~static~ wrapper at all?
  #+begin_quote
  Mechanically, yes - nothing stops you from adding more ~static~
  methods (a task function, ~main~) directly to =Stopwatch=. It would just
  become both the reusable timer *and* the test driver in one class, the
  same pattern the very first =Greeting= class used before it got split
  into =Greeting= + =GreetingTest=.

  Two separate reasons this wasn't the actual option here:

  1) *The submission rule itself* - the required public class name was
     =HarmonicTiming=, matching the mandatory filename
     =HarmonicTiming.java=. A top-level ~public class~ name must match
     its file, so submitting =Stopwatch.java= with a public class
     =HarmonicTiming= isn't legal Java at all. That closes the door
     regardless of design taste.
     
  2) *The design reason* - bolting task-specific logic and ~main~ onto
     =Stopwatch= is exactly the anti-pattern the =Greeting=/=GreetingTest=
     split was teaching against: it stops being a clean, reusable timer
     once every user of it also drags along your harmonic-number logic
     and entry point. A cleaner third option (not used here, but legal)
     would have been a second, *non-public* top-level =class Stopwatch=
     alongside =public class HarmonicTiming= in the same file - Java
     allows multiple top-level classes per =.java= file as long as only
     one is ~public~ and it matches the filename. That needs no
     ~static~ or nesting either, since top-level classes never carry an
     enclosing-instance reference in the first place.
  #+end_quote

- Code explanation:
  #+begin_quote
  1) *Collect:* loop =n= over a range that stays below the crash point
     (=12600=), so the loop does not die mid-collection. For each =n=,
     run =java HarmonicRecursive= with =n= as argument. Since
     =returncode == 0= means the program finished cleanly, parse
     =result.stdout= into a ~float~ and append both =n= and the value to
     two parallel lists.
  2) *Fit:* =np.polyfit(n_values, sum_values, 1)= fits a straight line
     (degree 1) through the collected points.
  3) *Plot:* ~scatter~ the raw points, then draw the fitted line on top
     using the same =n_values=. A list comprehension computes the
     y-values of the line.
  #+end_quote

- These two plots only check facts about harmonic numbers. They say
  nothing about loop versus recursion, or about the crash.
  1) Plot 1 shows that the growth is not linear.
  2) Plot 2 shows that H_n grows like ln(n).

- A plot that connects to the exercise should show time against n, or
  the crash point across repeated fresh-JVM runs.
