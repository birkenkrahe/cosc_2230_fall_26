* What's object-oriented programming (OOP) about?

- Practically, for you right now:
  #+begin_quote
  + You can define your own data type with ~class~
  + You can create instances with ~new~ and call them with dot-notation
  + You can use library types the same way (e.g. ~String~)
  + You can compose your own types into a bigger program
  + You can hide implementation and hand clients an interface (API)
  #+end_quote

- Technically, as a programming paradigm:
  #+begin_quote
  + A way of organizing a program around objects
  + Bundling data and operations on that data instead of procedures that pass
    passive data structures around
  + An object owns some state and is responsible for keeping it
    consistent
  + Object exposes a contract (interface) and hides its representation
    (encapsulation)
  + You get work done by sending messages & which code runs can depend
    on the object's type
  + The object's type is decided at run time (polymorphism/dynamic
    dispatch)
  + Types relate by inheritance/subtyping so one piece of client code
    works with many kinds of object
  #+end_quote

- Technically, in Java:
  #+begin_quote
  + ~class~ is a blueprint; ~new~ builds an object on the heap, used via dot-notation
  + State lives in instance fields, behavior in instance methods; ~this~
    is the current object
  + A constructor (class name, no return type) sets up the object's
    initial state
  + Encapsulation is compiler-enforced: ~private~, package-private
    (default), ~public~
  + Every class implicitly extends ~Object~ and may ~implements~ an
    ~interface~ (a bodiless contract)
  + Which implementation runs is picked at run time from the object's
    real class (dynamic dispatch)
  + Non-primitive types are reference types; the eight primitives
    aren't objects (wrapper classes + autoboxing bridge them)
  + ~final~ means assign-once; ~static~ means belongs to the class, not an
    instance
  + Objects are freed automatically (garbage collection); classes
    group into packages and ship as ~jar~ files
  #+end_quote

We'll look at each of these as part of a simple and an extended
example, followed by in-class practice exercises and a home assignment
to test your understanding (or your memory).

* Reference data types, wrappers, and primitive types

- What is a *reference [data] type*?
  #+begin_quote
  A reference data type is a data type that consists of *data*,
  *constructors*, and *methods*. The constructor is used to create *objects*
  of the data type; the *data* signify the *state* of the object, and the
  *methods* allow to change the object's *behavior*. They are called
  *reference* types because a variable of that type doesn't hold the
  object itself - it holds a *reference* to it.

  In terms of *memory*: when you create (or *instantiate*) an object of a
  reference type, the machine keeps track of the object using a
  reference, a link, or an address to a region of memory. *An object is
  a state machine.*

  Integers (~int~) are also data types, but they are primitive,
  non-reference data types. They aren't objects at all.
  #+end_quote

- What about other languages?
  #+begin_quote
  + Primitive vs. reference type is Java (and C#) specific
  + In Python, Javascript, Ruby everything is a reference
  + C/C++ have aliases (~int&~) that are called references
  #+end_quote

- What's a *wrapper class*?
  #+begin_quote
  Every primitive type has a matching *wrapper* class (~int~ -> ~Integer~,
  ~double~ -> ~Double~, and so on), and a wrapper *is* a real reference
  type - it has a constructor, it lives on the heap, and a variable of
  that type holds a reference to it, not the value itself.

  Java blurs the line on purpose: *autoboxing* automatically converts a
  primitive into its wrapper wherever a reference type is expected
  (=Integer i = 5;=), and *unboxing* converts back (=int j = i;=).
  You'll meet this soon: Chapter 4's generic collections, like
  =Stack<Integer>=, can only ever hold reference types - =Stack<int>=
  doesn't compile, =Stack<Integer>= does - and autoboxing is what makes
  =stack.push(5)= work anyway, with no visible conversion in your code.

  =Integer.parseInt(String)= is different: it is an explicit *method call*
  that parses text into a primitive =int=.  Autoboxing is an *implicit*
  conversion the compiler inserts for you, primitive to wrapper, with
  no method call written anywhere (=Integer i = 5;=).
  #+end_quote

- C++ is an object-oriented superset of the C language. It is arguably
  more popular and used more nowadays than Java. C++ compiles to a

** =Greeting= in Python

- Python is the most popular high level language. It is written in C,
  and it is an interpreted rather than compiled language - that means
  that the user does not need to translate the code to machine
  code. Under the hood, CPython compiles the source to bytecode, which
  is then interpreted by a virtual machine (like Java, except that
  there is no compile-time type checking). There are no separate build
  artifacts (like ~.class~ or ~.jar~). Much slower than both Java and C++.

- The code looks very different to C++ or Java:
  + No access modifiers like ~public~ or ~private~ (that is enforced)
  + Python is dynamically (not statically) typed: object data type is
    inferred and not explicitly stated.
  + No field declarations up front (like =String greeting=): ~__init__~
    creates =self.greeting= immediately, there is no static type checker
    enforcing that every instance has this attribute.
  + ~self~ is explicit everywhere. Java's equivalent (~this~) is implicit
    unless needed. ~self~ is required as first parameter of every
    instance method and used to access fields.
  + ~main~ is just a function, not special as unique entry point.
  + No ~System.out.println~, just ~print~. ~str()~ is called implicitly
    similar to how Java's ~println~ calls ~toString()~.

- Code:
  #+begin_src python :results output :exports both :session *Python* :python python3
    class Greeting:
        def __init__(self, s):
            self.greeting = s

        def get_greeting(self):
            return self.greeting


    def main():
        greet = Greeting("hello world")
        print(greet.get_greeting())


    if __name__ == "__main__":
        main()
  #+end_src

  #+RESULTS:
  : hello world

* Interfaces and polymorphism

- What does *interface vs. implementation* actually look like in code -
  not just as a design principle, but as a language mechanism?
  #+begin_quote
  A Java ~interface~ declares a contract - method signatures with no
  bodies - that any class can promise to fulfill with ~implements~.
  Once a class implements an interface, you can hold a reference to
  one of its objects using the *interface* type instead of the concrete
  class type. Which method body actually runs is decided at *run-time*,
  based on the real object's class, not the declared type of the
  variable holding it. This mechanism is called *polymorphism* (or
  *dynamic dispatch*).
  #+end_quote

- Why does this matter for what's coming?
  #+begin_quote
  ~Stack~ and ~Queue~ classes are built on exactly this mechanism. Both
  implement Java's built-in =Iterable<Item>= interface, which requires
  exactly one method, =iterator()=, returning an object that itself
  implements =Iterator<Item>= (~hasNext()~ and ~next()~). That one small
  interface contract is what lets you write =for (String s : stack)=
  instead of manually indexing into the stack's internals - the
  ~for~-each loop works by calling =iterator()=, =hasNext()=, and =next()=
  through the interface, without knowing or caring whether =Stack= is
  actually implemented with an array or a linked list underneath. Same
  idea as =Greeter= below - just applied to something you'll be building
  yourself soon.
  #+end_quote

- A minimal example: one interface, two unrelated implementations.

- First, the contract itself - just a name and a method *signature*, no
  body at all. This compiles on its own but does nothing yet; it only
  says "anything that calls itself a =Greeter= must have a =sayHello()=
  method that returns a =String=."

  #+begin_src java :tangle ../src/Greeter.java :noeval :no-expand
    public interface Greeter
    {
        String sayHello();
    }
  #+end_src

- Now the first class that *keeps* that promise. Note ~implements
  Greeter~ in the class header - that's the only thing linking this
  class to the interface above.

- Neither =FormalGreeter= nor =CasualGreeter= knows the other exists - the
  only thing tying them together is the shared =Greeter= contract. The
  loop in =GreeterTest= never mentions either concrete class by name;
  =g.sayHello()= calls whichever implementation the *actual* object in
  that array slot has, decided at run-time. That's the payoff: code
  written once against the *interface* keeps working unchanged if you
  add a third, fourth, tenth =Greeter= later.

- A note on *abstract classes*: Java has a second mechanism for this
  same idea, ~abstract class~ - a class that, like an interface, can
  declare methods with no body, but, unlike an interface, can also
  hold state and provide ready-made methods for subclasses to inherit.

  This course's textbook *doesn't use them anywhere* - every
  polymorphism example in Sedgewick & Wayne is built on
  *interfaces*. If you see =abstract class= elsewhere - other courses,
  other code - it's solving this same problem with a different,
  heavier tool, not a concept you're missing from here.

* Questions and answers

1) What's the meaning of ~public static void main(String[] args)~?
   #+begin_quote
   1) ~public~: this function can be seen and called from anywhere in the
      program.
   2) ~static~: this function belongs to the ~class~ itself, not to any
      particular object of it, so it can be called without first
      creating an instance (needed here because no object exists yet)
   3) ~void~: this function has no return value
   4) ~main~: this is the mandatory name for the program's entry point
   5) ~String[] args~: this is an array of strings representing the
      (optional) arguments to the program on the command-line
   #+end_quote
2) Why can't a constructor be called =public void Greeting(String s)=
   if it does not return anything?
   #+begin_quote
   A constructor has no return type at all - not even ~void~. Java
   recognizes a constructor by two things together: the name exactly
   matches the class name, and there is no return type in front of
   it. Adding ~void~ turns it into an ordinary method that happens to
   share the class's name (Java allows that) - it is no longer a
   constructor.

   Since =Greeting= would then have zero constructors, =javac= silently
   supplies its own implicit no-argument one: =Greeting()=. The line
   =Greeting greet = new Greeting("hello world");= from the code-along
   would now fail to *compile* - "constructor Greeting in class
   Greeting cannot be applied to given types" - because no
   constructor accepts a =String= anymore. The ~void~ method would have
   to be called separately, like any other method, after first
   constructing an (uninitialized) object with =new Greeting()=:
   =greet.Greeting("hello world");=
   #+end_quote
3) Why is =start= declared ~final~?
   #+begin_quote
   =start= is set once, in the constructor, and should never change
   for the rest of the object's life - the whole point is that it
   records a fixed moment in time. Declaring it ~final~ makes the
   compiler enforce that guarantee, instead of just trusting that no
   method ever reassigns it by accident.
   #+end_quote
4) Why can't we just reuse the =timer1= object for =time2=?
   #+begin_quote
   Because =start= is ~final~. To reuse the timer object, we would need
   to add a method that can reset the time (home assignment).
   #+end_quote
5) What if we wanted to run this with fixed =N= (as a constant)?
   #+begin_quote
   Add =private static final int N = 100000000;= before =start=. The
   difference is that =start= is an *instance* field (every =Stopwatch=
   object gets its own =start=) while =N= is =static= because it is
   available globally across the class.
   #+end_quote
6) At which decimal are the first two results beginning to differ?
   #+begin_quote
   Reading the =%.2f= output directly: =0.46= vs =0.47= (and =4.55= vs
   =4.70=) - both agree at the tenths place and first diverge at the
   hundredths place, the second decimal digit.
   #+end_quote
7) Why are the results for ~Math.sqrt()~ and ~Math.pow()~ different?
   #+begin_quote
   They're barely different, and that's itself the interesting
   result. The book (2017) reports =Math.sqrt()= as more than 10x
   faster than =Math.pow(x, 0.5)= - a huge gap, because =Math.sqrt()= is
   a narrow, specialized operation the JIT can optimize heavily
   (close to one hardware instruction), while =Math.pow(x, y)= has to
   stay correct for *any* exponent =y=, including negative, fractional,
   infinite, and NaN values - that generality costs real time.
   #+end_quote
8) Why can't I drop the parameters from ~main(Strings[] args)~ if I
   don't run the program with command line arguments?
   #+begin_quote
   Because the JVM finds the entry point by reflection, searching for
   one exact signature: ~public static void main(String[] args)~ -
   public, static, void, exactly one =String[]= parameter. That's a
   fixed runtime lookup, not a flexible match.

   =public static void main()= still *compiles* fine - it's a legal
   method, and =javac= has no opinion about entry points. But it's no
   longer the entry point: =java ClassName= searches for the exact
   signature, fails to find it, and the program never runs, whether
   or not the body ever uses =args=. (C++ can allow a no-argument
   =main()= because the compiler treats =main= as a small family of
   sanctioned signatures; Java has no such special-casing - there's
   exactly one accepted shape.)
   #+end_quote
9) What's the largest number you can use for =n=?
   #+begin_quote
   =args[0]= is parsed with =Integer.parseInt()= into an =int=, and the
   loop counter =i= is also an =int= - so the hard ceiling is
   =Integer.MAX_VALUE= = 2^31 - 1 = 2,147,483,647. Pass anything
   larger and =Integer.parseInt()= throws a =NumberFormatException=
   before the program even starts. (Even if =n= were widened to =long=,
   =i= would still overflow past =Integer.MAX_VALUE=, wrap to a negative
   number, and the loop condition =i <= n= would behave incorrectly -
   so the real constraint is the =int= loop counter, not just the
   parsed argument.)

   Below that hard limit, there's also a practical limit: how long
   you're willing to wait. =n = 1,000,000,000= already took over 4
   seconds here; =Integer.MAX_VALUE= would take roughly twice
   that. (Home assignment)
   #+end_quote
10) Why wrap the available function into a =Stopwatch= class?
    #+begin_quote
    The general answer: Data abstraction pays for itself. Concretely:
    - Intent at the call site. =timer1.elapsedTime()= says what you
      mean. The raw version makes every reader re-derive "oh, this is
      measuring elapsed time" from a subtraction and a =/1000.0=.
    - The arithmetic is written once, not copy-pasted everywhere. Every
      client that times something would otherwise repeat =(now - start) /
      1000.0= — and one client eventually forgets the =/1000.0= or gets the
      subtraction order backwards. Centralizing it means one place to
      get right.
    - The representation can change without breaking
      clients. =currentTimeMillis()= is wall-clock time, which can
      actually jump if the system clock gets adjusted (NTP sync, etc.) —
      =System.nanoTime()= is the more correct tool for measuring elapsed
      intervals since it's monotonic. If you ever want to fix that,
      change one line inside =Stopwatch=; every client using the class is
      unaffected.
    - You get independent instances for free. The demo runs =timer1= and
      =timer2= simultaneously, each tracking its own start time. Doing
      that with raw =currentTimeMillis()= calls means manually juggling
      =start1/start2= variables yourself with no grouping — the object
      gives you that bookkeeping automatically.
    #+end_quote
11) What has changed since JDK 17 (now: JDK 25)?
    #+begin_quote
    Both =Math.sqrt()= and =Math.pow()= are HotSpot *intrinsics*
    (hand-optimized, often assembly-level implementations the JIT
    substitutes for the plain Java method).  What changed between 17
    and 25 is the *quality* of the =pow= intrinsic itself: newer JIT
    releases regularly refine these hand-written fast paths
    (e.g. detecting more special-case exponents, using newer CPU
    instructions). Pinning down the exact JDK release and bug/JEP
    responsible would mean searching the OpenJDK issue tracker (JBS)
    directly, not general web search.

    We have solid *empirical* evidence (two reproducible runs) that
    something changed, without a confirmed *mechanistic* citation for
    exactly what or when.
    #+end_quote
12) What does the JIT do exactly?
    #+begin_quote
    The JIT (Just-In-Time compiler) is the part of the JVM that
    turns bytecode into native machine code *while the program
    runs*, instead of all at once ahead of time like =javac= does for
    source-to-bytecode.

    Java source (=.java=) compiles to bytecode (=.class=) once, ahead
    of time. But the JVM doesn't run that bytecode as machine code
    directly - it starts out *interpreting* it, instruction by
    instruction, which is slow. As the JVM runs, it profiles which
    methods get called a lot (like =Math.pow()= called 100 million
    times in a loop) and marks them "hot." The JIT then compiles just
    those hot methods down to optimized native machine code and
    swaps that in for all future calls - the rest of the program
    stays interpreted, since compiling code nobody runs repeatedly
    would waste time for no benefit.

    This is also where *intrinsics* come in (see Q11): for a handful
    of common methods, HotSpot doesn't even bother compiling the
    normal Java implementation - it substitutes a hand-written,
    highly optimized native version directly. =Math.sqrt()= and
    =Math.pow()= are both on that list, which is why their relative
    performance can shift between JDK releases as those hand-written
    versions get refined - the underlying Java source for =Stopwatch=
    or your test client never changes at all.
    #+end_quote
13) Can you explain what this code does?
    #+begin_example sh
    source $HOME/.sdkman/bin/sdkman-init.sh
    sdk use java 25.0.1-tem
    java -version 2>&1
    #+end_example
    #+begin_quote
    Line 1: loads SDKMAN's shell functions (=sdk=, =sdk use=, =sdk
    install=, ...) into the *current* shell process. =source= runs the
    script's commands directly in this shell rather than a child
    process, so whatever it defines stays defined afterward - a
    plain execution (=./sdkman-init.sh=) would lose everything the
    moment that child process exited.

    Line 2: switches which =java/javac= this shell's =PATH= resolves
    to - here, the installed candidate named =25-open= - for the rest
    of *this shell session only*. It does not touch =sdk default=, so
    nothing changes outside this one process.

    Line 3: prints the active JVM's version banner, to confirm the
    switch actually took effect before doing anything else. The
    =2>&1= matters: =java -version= writes its output to *stderr*, not
    stdout (an old convention predating =-version= being a
    well-behaved flag) - without redirecting stderr into stdout,
    some tools/contexts that only capture stdout would show nothing
    at all, even though the command ran correctly.
    #+end_quote
14) When does a nested class need to be declared ~static~, and when
    does that question not even apply?
    #+begin_quote
    A non-~static~ nested class carries a hidden reference to one
    specific instance of its *outer* (enclosing) class - it can only be
    created via =outer.new Inner()=, from code that already has an
    =outer= instance to attach to. If the code creating it runs in a
    ~static~ context (like ~main()~), no instance of the outer class
    exists yet, so there is nothing for that hidden reference to point
    to. Marking the nested class ~static~ removes the hidden reference
    entirely, letting it be created on its own - =new Inner()= - just
    like an ordinary class.

    A *top-level* class (one that isn't nested inside anything at all)
    never needs this modifier, because the question "does it need a
    reference to its outer class" doesn't even arise: there is no
    outer class in the first place. (Note: "outer class" here is
    unrelated to *superclass* - there's no ~extends~ or inheritance
    involved at all.)
    #+end_quote
15) Why can a recursive method eventually crash with a
    =StackOverflowError=, while an equivalent iterative (loop-based)
    method never does, no matter how large the input?
    #+begin_quote
    Each recursive call pushes a new *stack frame* - a region of the
    call stack holding that call's parameters, local variables, and
    return address. None of these frames are freed until the base case
    is reached and the whole chain of calls starts unwinding, returning
    values back up. The deeper the recursion goes before hitting the
    base case, the more frames pile up simultaneously, all still
    "open." The call stack has a fixed size (adjustable with the ~-Xss~
    flag, but always finite) - so with enough recursion depth, it runs
    out of room: =StackOverflowError=.

    A loop-based version is different: the method containing the loop
    is called *once*, creating exactly *one* stack frame. The loop body
    runs many times, but that's just repeated execution of statements
    inside that single, already-existing frame - no new frame is
    pushed per iteration. Memory usage stays flat regardless of how
    many times the loop runs, which is why an iterative solution can
    handle inputs far larger than a recursive one before hitting any
    hard limit.
    #+end_quote
16) When =javac= compiles cleanly (no errors, =.class= files produced),
    what exactly does that guarantee - and what does it *not*
    guarantee?
    #+begin_quote
    A clean compile means the code passed every *compile-time* check:
    - *Syntax* - correct grammar (braces, semicolons, ...).
    - *Type checking* - you can't assign a =String= to an =int=, or pass
      an argument of the wrong type.
    - *Name resolution* - every identifier (variable, method, class)
      must be declared or importable.
    - *Compile-time-checkable access rules* - e.g. calling a ~private~
      member from outside its class.
    - A few structural rules - e.g. every path through a non-~void~
      method must ~return~ something; code placed after a ~return~ is
      unreachable and rejected.

    It does *not* guarantee:
    - Correct *logic* - the program can compile cleanly and still
      compute the wrong answer.
    - Freedom from *run-time* errors - things like
      =NullPointerException=, =ArrayIndexOutOfBoundsException=, or
      =StackOverflowError= are never caught at compile time, only when
      the running program actually hits them.

    "=javac= success" means *valid, type-safe Java* - not "this program
    does what I intended."
    #+end_quote
