* The problem: whitelist filter

** Blacklists and whitelists

- *Blacklist*: entities to be *rejected* (overdrawn accounts, spammers).

- *Whitelist*: entities to be *accepted* (accounts in good standing,
  friends and relatives).

- A whitelist must be complete.

- A blacklist only needs to catch bad actors.

** The filter: an email example

- *Filter:* read the whitelist from a file; read strings from ~StdIn~;
  write to ~StdOut~ only those on the whitelist.
- The blacklisted emails are rejected.
- The whitelisted emails are accepted.

*** Question: When would you use a whitelist rather than a blacklist?

**** Answer                                                           :skip:

#+begin_quote
- *Whitelist* = "default deny": use when the good set is small and known
  and a false accept is costly. Examples: firewall allowing only
  certain IPs/ports, corporate application control (only approved
  programs run), input validation (allowed characters/file types),
  parental controls, badge readers, approved merchants.
- *Blacklist* = "default allow": use when the good set is huge or
  open-ended (spam filters, ad blockers).
- *Punchline:* a whitelist *fails safe* (unknown → rejected), a blacklist
  *fails open* (new threat → accepted).
- Terminology: many style guides (NIST, Google, Linux kernel) now use
  *allowlist/denylist*. You will see both.
#+end_quote

** Question: Why doesn't it find anything?

*** Answer                                                             :skip:

- ~==~ on reference types compares *references* (memory addresses),
  not character sequences. ~words[i]~ and ~key~ are different ~String~
  objects that happen to hold the same characters.

- Arrays and strings are reference types: they store references
  (pointers), not values.

- With string *literals*, ~==~ can appear to work, because Java
  interns literals. The bug shows up here only because both strings are
  read at runtime from a file and from ~StdIn~.

  #+begin_src java

    String b = "cat";
    System.out.println(a == b); // true  - interned literals, same object

    String c = new String("cat");
    System.out.println(a == c); // false - same characters, different object
  #+end_src

* Theory: mathematical model

Why mathematical analysis?

#+begin_quote
Before going into production with a program, we need to estimate the
total cost. This is followed by an empirical (doubling) test to
confirm (or deny) our hypothesis.
#+end_quote

** Model

- Distinguish between *workload* (transactions) and the *cost* per search.

- The total time = (number of searches) x (cost per search)

- N strings on the whitelist.

- Number of searches first: cN transactions for a constant c. This is
  an *assumption about the workload* (more customers → more traffic),
  not something derived from ~search()~.

- For example, a business could have N = 1,000 whitelisted email
  accounts but 5,000 login attempts daily: c = 5

- Assumption: string length not long, L << N, so each ~compareTo()~
  costs about constant time. That lets us use *number of compares* as
  the *cost model*.

- What if string length was long?
  #+begin_quote
  ~compareTo()~ would no longer cost constant time - it costs time
  proportional to how many characters it has to check before finding a
  difference (up to string length L). Our cost model would have to
  include the factor L.
  #+end_quote

** Two kinds of search (definitions)

- The search algorithm we implemented is completely deterministic: it
  always scans each index until it finds something or falls off the end.

- For the purpose of average-case analysis, we need weights: the cost
  of search depends on the input - 1 compare if the key is first, N
  compares if the key is last.

- To average those costs you have to say how likely each input is:
  that's a *probability distribution*, and the average-case cost is an
  *expected value*: E[compares] = \sum P(key at position i) * i - a
  weighted sum.

- There are two interesting cases:
  1. *Random search hit*: the key IS on the whitelist, and each of the N
     entries is equally likely to be the key (probability 1/N).
  2. *Random search miss*: the key is NOT on the whitelist (e.g., the
     spam address, which cannot be found among the allowed addresses).

** Question: How many compares does a random search hit need on average?

| Key at position | Compares |
|-----------------+----------|
| 1               | 1        |
| 2               | 2        |
| ...             | ...      |
| N               | N        |

*** Answer                                                             :skip:

- Simple example: N = 4
  #+begin_example
  Compare counts at each slot: 1, 2, 3, 4
  Sum = 1 + 2 + 3 + 4 = 10
  Average = sum / N = 10 / 4 = 2.5

  The average is the sum of all outcome values / number of outcomes
  (same as multiplying with the probability for one single outcome)
  #+end_example

- Each position has probability 1/N, so the expected value (average
  number of compares, or weighted average of the compare count) is:
  #+attr_html: :width 400px :float nil:
  [[../img/expected_value.png]]

  \[ \frac{1}{N}\sum_{i=1}^{N} i = \frac{1}{N}\cdot\frac{N(N+1)}{2} = \frac{N+1}{2} \sim \frac{N}{2} \]

- Common mistakes:

  + Gauss gives the *sum* N(N+1)/2. The *average* is the sum divided by N
    (multiplied by 1/N, not divided by 1/N).

  + Write ~N/2 (tilde notation keeps the constant), not "O(N/2)".
    Big-O drops constants, so it would just be O(N). Without the
    constant, you cannot actually predict the number of compares.

  + The ~N/2 figure depends on the uniform assumption. If searched
    keys cluster near the front of the list, hits are cheaper; near
    the back, more expensive.

- The Gauss pairing trick again: write the sum forwards and backwards,
  then add:

** Question: Why does a search miss check all N strings?

A search miss means that the key is not found. Look at the code:

#+begin_src java
  for (int i = 0; i < a.length; i++)
      if (a[i].compareTo(key) == 0) return i;   // only early exit
  return -1;
#+end_src

*** Answer                                                             :skip:

- The only early exit fires on a match. On a miss, no compare ever
  matches, so the loop runs to completion: exactly N compares, then
  ~return -1~. (It does return, just not early.)

- There is no averaging and no probability involved here.

- Deeper reason: in an *unsorted* array, after N−1 unsuccessful checks
  the last entry could still be the key. You can't say "not here"
  until you've looked everywhere.

- Sedgewick says "on average" for the miss, but the miss cost doesn't
  vary: it is exactly N every time.

- Teaser: in a *sorted* array you could stop early. That's the idea
  behind binary search.

- Book connection: the book's exception filter in §4.2 prints the keys
  that are *not* on the whitelist, so every line it prints is a miss
  that paid the full N.

** Question: Each search is linear. Why is the running time quadratic?

*** Answer                                                             :skip:

N appears twice:
1. cost per search ~ N/2 (hit) to N (miss): linear in N
2. number of searches = cN: also linear in N

Total = cN × ~N = ~cN^2.

- With a *fixed* number M of transactions, the total would be ~MN,
  which is linear in N. The quadratic comes from traffic growing with
  the whitelist.
- Doubling N means twice as many searches, each twice as long:
  2 × 2 = 4. That's the prediction for the doubling test.

** Constant vs. notation distinction

- This lesson uses two unrelated constants, and it's easy to reach
  for the wrong one.

  1) The constant c in cN transactions is a *workload* assumption: it
     says the number of incoming searches scales with the whitelist
     size N, with c just the traffic-to-list ratio (e.g. 5000
     transactions against a 1000-entry whitelist gives c = 5).

  2) The constant a in the doubling-hypothesis form T(N) ~ aN^b is
     a *hardware* fact: it absorbs machine speed when converting operation
     counts into wall-clock seconds, and it cancels out of the
     doubling ratio T(2N)/T(N).

- Neither has anything to do with why we write ~N/2 instead of
  "O(N/2)" for the search-hit cost - that's a choice of *notation*, not
  a constant in a model.

- Big-O only bounds the *order* of growth and discards multiplicative
  constants, so N/2 and 100N are both O(N); that's fine for
  classifying an algorithm's growth class, but useless for predicting
  an actual compare count.

- Tilde notation keeps the leading constant, so ~N/2 lets us say
  something a plain O(N) can't: a hit costs about half of what a miss
  costs, and that difference is exactly what the doubling test later
  confirms empirically.

* Code-along: random input generator

** Generator

Start by coding the client program first.

#+begin_src java :tangle ../src/Generator.java
  // Generator.java - draw random strings from alphabet
  public class Generator
  {
      // random string of length L drawn from alpha
      public static String randomString(int L, String alpha)
      {
          // allocate an array to hold L characters, one per position
          char[] a = new char[L];
          // fill array positions 0 through L-1
          for (int i = 0; i < L; i++)
            {
                // pick a random index into alpha
                int t = StdRandom.uniformInt(alpha.length());
                // copy the character at that random index into slot i
                a[i] = alpha.charAt(t);
            }
          // build and return a string from the filled char array
          return new String(a);
      }

      public static void main(String[] args)
      {
          int N = Integer.parseInt(args[0]);      // how many strings
          int L = Integer.parseInt(args[1]);      // length of each string
          String alpha = args[2];                 // alphabet to draw from
          for (int i = 0; i < N; i++) // generate and print N strings
              StdOut.println(randomString(L, alpha));
      }
  }
#+end_src

** Duplicates

 Why are duplicates likely in the first run but not the second?
 
- Possible strings = |alphabet|^L:

  + 3 characters, length 3: 3^3 = 27 possible strings. Drawing 10
    gives about an 85% chance of at least one duplicate:
    #+attr_html: :width 600px :float nil:
    [[../img/birthday.png]]

    With 10 draws, the product has 10 factors and the last is 27-9=18.

  + 10 digits, length 8: 10^8 = 100 million. Drawing 15 gives
    essentially no chance of a duplicate.

- Why it matters: some search/sort algorithms perform differently
  depending on the duplicate rate. The generator lets us control it.

- This will come back when we talk about hashing and hash tables: hash
  collisions are exactly the birthday-paradox math. A hash table with
  M buckets and n keys starts seeing collisions once n approaches
  \sqrt{M}.

- In our example: M is the number of possible strings, and n is the
  number of strings drawn.

* Whitelist filter scenario: doubling test

- We build a test client that runs 10 * N searches (c = 10).

- Keys are drawn from the whitelist (every search is a hit) and there
  is no output except the time.

- This measures the ~N/2 case (we don't have to require keys not in
  the whitelist).

** Test client

- =TestSS.java= can only produce hits: the 10N searches all pay the
  N/2 average cost.

- The doubling happens later, when we run the test client!

#+name: TestSS.java
#+begin_src java :tangle ../src/TestSS.java
  public class TestSS
  {
      // sequential search
      public static int search(String key, String[] a)
      {
          // loop over the whole array
          for (int i = 0; i < a.length; i++)
              // if array element matches the key, return its index
              if (a[i].compareTo(key) == 0) return i;
          // if key is not found, return -1
          return -1;
      }

      public static void main(String[] args)
      {
          // read the whitelist from stdin into an array
          String[] words = StdIn.readAllStrings();
          // N is the size of the whitelist
          int N = words.length;
          // record the start time, in seconds
          double start = System.currentTimeMillis() / 1000.0;
          // run 10N searches total - c = 10, so workload scales with N
          for (int i = 0; i < 10*N; i++)
            {
                // pick a key at random from the whitelist itself - always a hit
                String key = words[StdRandom.uniformInt(N)];
                // this should never print - every search must find its key
                if (search(key, words) == -1)
                    StdOut.println(key);
            }
          // record the end time
          double now = System.currentTimeMillis() / 1000.0;
          // report total elapsed time for all 10N searches
          StdOut.printf("%.2f seconds%n", now - start);
      }
  }
#+end_src

* Summary

- *Client vs. implementation.* The client (=WhiteFilter=, =TestSS=)
  stays the same; the ~search()~ implementation decides whether the
  filter scales.

- *Strings.* ~==~ compares references, not characters. Use ~equals()~,
  or ~compareTo()~, which also tells you the order (smaller, equal,
  larger) - binary search will need that.

- *Cost model.* We count compares. A random search hit costs ~N/2
  compares on average; a search miss costs exactly N, because an
  unsorted array allows no early exit.

- *Workload.* cN searches x ~N compares each = ~cN^2 in total (between
  ~cN^2/2 for all hits and cN^2 for all misses): quadratic.

- *Experiment.* The doubling test confirms it: ratio -> 4, so b = lg 4
  = 2. Sedgewick's extrapolation: 1.28 million entries would take more
  than 10 hours. Sequential search does not scale.

- *All misses.* The ratio stays ~4 (same order of growth), but the
  times double (constant 1 instead of 1/2). Tilde notation keeps that
  constant; big-O would hide it.

- *Benchmark discipline.* A test should check its own premise: the hit
  counter in =TestSSMiss= must print 0.

- *Next: binary search.* On a sorted array, each compare halves the
  interval: at most floor(lg N) + 1 compares per search (20 for N =
  1,000,000), so ~cN lg N in total. It scales.

* Glossary

| Term                 | Definition                                           |
|----------------------+------------------------------------------------------|
| allowlist / denylist | newer names for whitelist / blacklist, used by many  |
|                      | style guides (NIST, Google, Linux kernel).           |
| benchmark            | a program that measures the running time of other    |
|                      | code, like =TestSS=.                                   |
| big-O notation       | an upper bound on the order of growth that drops     |
|                      | constant factors: N/2 and 100N are both O(N).        |
| blacklist            | a list of entities to be rejected ("default allow"). |
| client               | a program that uses a method or data type through    |
|                      | its contract, without depending on how it is         |
|                      | implemented.                                         |
| compare              | one test of a key against an array entry; the unit   |
|                      | of our cost model.                                   |
| ~compareTo()~          | ~s.compareTo(t)~ returns a negative int, 0 or a        |
|                      | positive int if s comes before, equals or comes      |
|                      | after t.                                             |
| cost model           | the operation we count instead of measuring time,    |
|                      | here: compares. Valid if each compare costs about    |
|                      | constant time.                                       |
| doubling test        | run a program for N, 2N, 4N, ... and compute the     |
|                      | ratio T(2N)/T(N); if T(N) ~ aN^b, the ratio          |
|                      | approaches 2^b.                                      |
| ~equals()~             | compares two strings character by character; true if |
|                      | they hold the same characters.                       |
| filter               | a program that reads input and writes only the items |
|                      | that pass a test, e.g. the strings on a whitelist.   |
| floor                | rounding down to a whole number: floor(19.93) = 19.  |
| interning            | Java stores identical string literals only once, so  |
|                      | ~==~ can appear to work on literals - but not on       |
|                      | strings read at runtime.                             |
| key                  | the value a search looks for.                        |
| lg N                 | logarithm base 2: the power to which you raise 2 to  |
|                      | get N, or how often you can halve N until you reach  |
|                      | 1. lg 8 = 3.                                         |
| order of growth      | how the running time grows with N, ignoring constant |
|                      | factors: here quadratic, N^2.                        |
| reference type       | a type whose variables store references (addresses)  |
|                      | to objects, e.g. ~String~ and arrays; ~==~ compares      |
|                      | those references.                                    |
| search hit           | the key is in the array; random hit: every position  |
|                      | equally likely.                                      |
| search miss          | the key is not in the array; sequential search then  |
|                      | checks all N entries.                                |
| sequential search    | check the entries one after the other until the key  |
|                      | is found or the array ends.                          |
| tilde notation       | f(N) ~ g(N) means f(N)/g(N) -> 1 as N grows; keeps   |
|                      | the leading constant: ~N/2.                          |
| token                | a run of non-whitespace characters; what             |
|                      | ~StdIn.readString()~ returns.                          |
| whitelist            | a list of entities to be accepted ("default deny").  |
| workload             | the number of searches the client performs, here cN. |
