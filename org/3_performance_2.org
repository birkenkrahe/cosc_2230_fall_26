- Can we guess the chances to find a three-sum depending on the range
  R = [-M,M) of our uniform distribution?
  #+begin_quote
  If we assume that the possible sums are uniformly spread out (we
  expect to find them with equal probability anywhere in R), the
  chance to find any one such triple is 1/R - it goes down with R.

  So we expect to find many more three-sums in a small R than in a
  large R.
  #+end_quote

* Making time for ~time(1~)

- Why is the running time the same?
  #+begin_quote
  The *count* swings wildly (60,000 vs. 70 -- roughly the same 1000x
  ratio as the range itself, matching the 1/R guess above), while the
  *running time* barely moves (0.122s vs.  0.124s) -- because =ThreeSum=
  does the same N^3 amount of work either way. The range changes what
  fraction of triples happen to sum to zero; it has no effect on how
  many triples get checked.
  #+end_quote

- What does ~time~ writes to? How can you find out more?
  #+begin_quote
  ~time~ writes to ~stderr~, the standard error stream. To find out, look
  at the ~time(1)~ manual page (works on Linux, MacOS):
  #+end_quote
  #+attr_html: :width 600px :float nil:
  [[../img/man_time.png]]

- What's the difference between ~real~, ~user~, and ~sys~ time?
  #+begin_quote
  - ~real~: wall-clock time: how long you actually waited, start to
    finish. Includes time waiting on I/O, other processes, disk etc.
  - ~user~: CPU time spent executing your program's own code (user
    space, not kernel)
  - ~sys~: CPU time the kernel spent on the program's behalf (system
    calls: I/O, memory allocation, etc.)
  #+end_quote

- Look at ~real~, ~user~ and ~sys~ reporting times again. Notice anything?
  #+begin_quote
  The ~user~ time is larger than the ~real~ time - how is that possible?
  Because ~user~ sums CPU-seconds across all threads/cores, while ~real~
  is just wall-clock time for the whole run - your time experience.
  #+end_quote

- What does ~System.currentTimeMillis()~ measure?
  #+begin_quote
  The Java function uses ~real~ time, which is noisier. ~user~ is the more
  stable, since it isolates just the CPU work your program did. That's
  what you're trying to measure with =Stopwatch.elapsedTime()=.
  #+end_quote

* Demo: A =Makefile= so you stop deleting =.class= files by hand

- =make= reads a =Makefile= of *targets*: each target lists what it
  *depends on*, and a recipe to build it. If a target's file is newer
  than everything it depends on, =make= skips the recipe -- that's the
  whole trick, and it replaces =rm -rf *.class= entirely.

- To run this on Windows, you need to install ~make~[fn:2]

  #+begin_src makefile :tangle ../src/Makefile :noeval -i
    # CP: classpath used for every compile/run (this dir, plus the jar)
    CP = .:stdlib.jar

    # Pattern rule: X.class depends on X.java. make only recompiles a file
    # if its .java is newer than its .class -- no more `rm -rf *.class`.
    %.class: %.java
    javac -cp $(CP) $<

    # Data files depend on RandomInts.class, not on each other -- change
    # RandomInts.java and both get regenerated next time they're needed.
    # Same N (1000) in both -- only the range M differs, so any
    # difference in ThreeSum's count is caused by the range, not by N.
    ../data/smallR.txt: RandomInts.class
    java -cp $(CP) RandomInts 1000 1000 > $@

    ../data/largeR.txt: RandomInts.class
    java -cp $(CP) RandomInts 1000000 1000 > $@

    # Time ThreeSum against both data files. Depends on ThreeSum.class and
    # both data files, so `make run` rebuilds exactly what changed.
    run: ThreeSum.class ../data/smallR.txt ../data/largeR.txt
    time java -cp $(CP) ThreeSum < ../data/smallR.txt
    time java -cp $(CP) ThreeSum < ../data/largeR.txt

    clean:
    rm -f *.class

    .PHONY: run clean
  #+end_src

* Checking the timing pattern

- Now we're keeping the large range of =M = 1,000,000= and vary only the
  number =N= of numbers that form triples. What happens if we double the
  number on the same range (same probability of hitting a three-sum)?
  #+begin_quote
  Since we have to check C(N,3) combinations, if the number =N= doubles,
  the number of combinations, being proportional to N^{3} octuples (it's
  cubic in N): C(2N,3)/C(N,3) = 4(2N-1)/(N-2) \approx (2N)^{3}/N^{3} -> 8 as N ->
  \infty. At N=1000 specifically 4 * 1999 / 998 \approx 8.01.
  #+end_quote

- What did we observe?
  #+begin_quote
  The triple counts will differ for every run -- the input is
  random. The timing pattern is the point, not the count: doubling =n=
  to roughly 5-6 times longer here, not 2 times.

  Why not 8 times as predicted? Because each ~time java...~ call spins
  up a brand-new JVM. You pay a fixed startup cost (classloading, JIT
  warm-up) before it does any real work. The overhead gets added.
  #+end_quote

* Code-along: =DoublingTest=

- The ~time~ function is a blunt instrument - it includes process
  start-up, JIT warm-up, and whatever else the OS is doing.

- We're going to use our own =Stopwatch= class (not the library copy).

- Do we need to extract the ~class~ definition of =Stopwatch=, or can we
  use =Stopwatch.java= with the ~main~ test client nested inside?
  #+begin_quote
  The class has no ~static~ initializer, so nothing runs on
  ~load~. Another class could still call ~main~ directly:
  =Stopwatch.main(new String[]{"1000"})= - since it's ~public static~, and
  it would run the ~sqrt~ / ~pow~ test.
  #+end_quote

- The =DoublingTest= ~class~ prints a table of doubling *ratios* for the
  three-sum problem. The table shows how doubling the problem size
  affects the running time of the method call =ThreesSum.countTriples()=
  for problem sizes starting at N=512 and doubling for each row of the
  table.

- Code:
  #+begin_src java :dir src :tangle ../src/DoublingTest.java :noeval :cmpflag "-cp .:stdlib.jar" :cmdline "-cp .:stdlib.jar"
    // DoublingTest.java prints table of doubling ratios for ThreeSum.java
    public class DoublingTest
    {
        // time ThreeSum
        public static double timeTrial(int n)
        {
            // create static array of n elements
            int[] a = new int[n];
            // initialize array with uniformly random integers
            for (int i = 0; i < n; i++)
                a[i] = StdRandom.uniformInt(-1000000, 1000000);
            // create a Stopwatch timer
            Stopwatch timer = new Stopwatch();
            // count the number of triples that add up to zero
            int count = ThreeSum.countTriples(a);
            // return elapsed time
            return timer.elapsedTime();
        }
        // test client
        public static void main(String[] args)
        {
            // stop after max time trials (input)
            int max = Integer.parseInt(args[0]);
            // loop over n time trials starting at 512
            for (int n = 512; n <= max; n *= 2)
                {
                    double previous = timeTrial(n / 2); // time at half size
                    double current  = timeTrial(n);  // time at full size
                    double ratio = current / previous;
                    StdOut.printf("%7d %4.2f\n", n, ratio);
                }
        }
    }
  #+end_src

- Observation:
  #+begin_quote
  The ratio wobbles at small n and settles in *near* 8 by n = 1,000-2,000.
  It is not exactly 8, and it will not match the textbook's table digit
  for digit either (the book's own values are 6.48, 8.30, 7.75, 8.00,
  8.05 - a single run on the authors' machine). Why:
  - Each ratio compares two measurements from ~Stopwatch~, which counts
    whole milliseconds; wall-clock time also picks up JIT compilation,
    garbage collection, other processes and CPU speed changes.
  - Every ~timeTrial~ builds a fresh random array. The work is the same
    (all triples are checked), but the data differs from run to run.
  - Warm-up: the first calls run in the slower interpreter before the JIT
    compiles ~countTriples()~, which distorts the small-n rows most.
  - The exact ratio C(2N,3)/C(N,3) = 4(2N-1)/(N-2) is itself not 8 (8.01
    for N=1024); it only approaches 8 as N grows.
  - The machine matters: cache sizes, clock speed and background load
    differ from computer to computer.
  Small deviations from 8 (a few percent) are therefore what measurement
  noise looks like - the cubic growth is confirmed.
  #+end_quote

    // Stopwatch.java: measure elapsed time during a computation
    public class Stopwatch
    {
        // Private final data - set once
        private final long start;
        // Constructor: set stopwatch to current system time
        public Stopwatch()
        {
            start = System.currentTimeMillis();
        }
        // Return elapsed time between start and now in seconds
        public double elapsedTime()
        {
            long now = System.currentTimeMillis();
            return (now - start) / 1000.0;
        }
        // Test client
        public static void main(String[] args)
        {
            // Input number of iterations n
            int n = Integer.parseInt(args[0]);

            // Compute and time computation using Math.sqrt(x)
            // Create a Stopwatch object
            Stopwatch timer1 = new Stopwatch();
            // Set sum to zero
            double sum1 = 0.0;
            // Loop from 1 to n
            for (int i = 1; i <= n; i++)
                // Add term to the sum
                sum1 += Math.sqrt(i);
            // Measure the elapsed time after the loop
            double time1 = timer1.elapsedTime();
            // Print total sum and elapsed time
            StdOut.printf("Math.sqrt(): %e (%.2f seconds)\n", sum1, time1);

            // Compute and time computation using Math.pow(a,b)
            Stopwatch timer2 = new Stopwatch();
            // Set sum to zero
            double sum2 = 0.0;
            // Loop from 1 to n
            for (int i = 1; i <= n; i++)
                // Add term to the sum
                sum2 += Math.pow(i,0.5);
            // Measure the elapsed time after the loop
            double time2 = timer2.elapsedTime();
            // Print total sum and elapsed time
            StdOut.printf("Math.pow(): %e (%.2f seconds)\n", sum2, time2);
        }
    }

  #+name: ThreeSum.java
  - This implements the iterative algorithm with the improvement
  #+name: ThreeSum.java v2
  #+begin_src java :dir src :tangle ../src/ThreeSum.java :noeval :cmpflag "-cp .:stdlib.jar" :cmdline "-cp .:stdlib.jar"
    // ThreeSum.java
    public class ThreeSum
    {
        // countTriples: input integer array, returns number of triples adding up to zero
        public static int countTriples(int[] a)
        {
            // define length of array
            int n = a.length;
            // set counter to zero
            int count = 0;
            // loop over array for first triple element
            for (int i = 0; i < n; i++)
                // loop over array for second triple element, starting after i
                for (int j = i+1; j < n; j++)
                    // loop over array for third triple element, starting after j
                    for (int k = j+1; k < n; k++)
                        // check if triple adds up to zero
                        if (a[i] + a[j] + a[k] == 0)
                            // increase counter
                            count++;
            // return counter
            return count;
        }
        // test client
        public static void main(String[] args)
        {
            // input array from command-line
            int[] a = StdIn.readAllInts();
            // compute number of triples that add up to zero
            int count = countTriples(a);
            // print result
            StdOut.println(count);
        }
    }
